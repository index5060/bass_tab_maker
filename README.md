# Bass Practice

베이스 연습용 로컬 웹앱. 탭 표시 · 속도 조절 · 원본/신디 전환 세 가지가 핵심.
서버 없음, 계정 없음, 파일은 전부 브라우저 IndexedDB 안에만 있습니다.

**YouTube 링크 하나로 베이스 탭까지:**

```
YouTube 링크 ──→ ① 음원 파일 ──→ ② 베이스 분리 ──→ ③ 베이스 탭 자동 생성
                 (yt-dlp)        (Demucs)           (basic-pitch / YIN)
```

사이드바 맨 위 **"YouTube 링크로 시작"**에 링크를 붙여넣고 "가져오기"를 누르면 세 단계가
자동으로 이어집니다. 각 단계 결과는 파일로도 받을 수 있습니다 — 음원(`.m4a`), 베이스
(`-bass.wav`), 탭(`.gp`, Guitar Pro · TuxGuitar · MuseScore에서 열림).
YouTube 쪽은 로컬 사이드카가 필요합니다 → [YouTube 링크 → 탭](#youtube-링크--탭)

## 실행

**Windows에서 제일 쉬운 방법: 프로젝트 폴더의 `start.bat`를 더블클릭.**
dev 서버와 사이드카가 각각 창으로 뜨고 브라우저까지 열립니다. 터미널이 어느 폴더에
있는지 신경 쓸 필요가 없습니다 — `npm run ...`은 프로젝트 폴더에서만 동작해서, 홈
폴더에서 실행하면 `package.json`을 못 찾았다는 ENOENT 에러가 납니다.

### 수동 실행

> **`index.html`을 더블클릭하면 안 됩니다.** 하얀 화면만 나옵니다.
> 브라우저가 `file://` 출처에서 ES 모듈 로딩을 CORS로 차단하기 때문입니다
> (상대경로로 바꿔도 안 됩니다 — 브라우저 차원의 제약입니다).
> 웹앱이라 반드시 서버로 띄워야 합니다.

```bash
npm install
npm run dev          # → http://localhost:5173  (이 주소를 브라우저에서 열기)
```

빌드된 버전을 보고 싶으면:

```bash
npm start            # vite build + vite preview 한 방에
```

테스트:

```bash
npm test             # 유닛 테스트 (싱크·스템 수학·음정·채보·링크, 175개)
npm run test:cold    # 콜드스타트 회귀 테스트 (실제 브라우저)
npm run test:cursor  # 재생 커서가 실제로 보이고 움직이는지
npm run test:stems   # cross-origin isolation + 스템 UI 전제조건
npm run test:degrade # 선택적 의존성이 빠져도 앱이 살아있는지
npm run test:diag    # isolation 진단이 진짜 원인을 짚는지 (헤더 빼고/넣고 양쪽)
npm run test:wiring  # 음원 붙이면 소스 버튼과 곡 목록이 살아나는지
npm run test:dup     # 새로고침해도 곡이 안 불어나는지 / 무음 폴백
npm run test:autotab # 자동 채보가 실제 앱에서 끝까지 도는지
npm run test:sidecar # 사이드카 프로토콜 + isolated 페이지의 교차 출처 호출
npm run test:youtube # 링크 → 음원 → 스템 → 탭 전 구간 + 파일 저장 + 실패 경로
MODE=preview npm run test:cold   # 빌드 경로까지

npm run replay -- 채보진단.json  # 진단 파일을 실제 채보 파이프라인에 다시 통과
```

> **버전을 새로 받으셨다면 `npm install`을 다시 실행하세요.** 의존성이 추가됐을 수 있습니다.

혹시 실수로 `index.html`을 직접 열더라도, 하얀 화면 대신 위 명령어를 알려주는 안내판이
뜨도록 해뒀습니다 (인라인 classic 스크립트는 `file://`에서도 실행되므로).

## 함정 하나 (이미 밟았음)

**첫 실행에서 악보가 아예 안 뜨는 버그가 있었습니다.** 원인이 재밌어서 기록해둡니다.

Vite는 dev 서버가 뜰 때 `publicDir`의 파일 목록을 **한 번 스냅샷**해두고 그걸로 서빙합니다.
그런데 `@coderline/alphatab-vite` 플러그인은 Bravura 폰트와 사운드폰트를 플러그인 훅에서
복사하는데, 그게 스냅샷 **이후**에 돕니다. 그래서 갓 clone/압축해제한 트리에서 첫
`npm run dev`를 하면 `/font/Bravura.woff2` 요청이 실제 폰트 대신 SPA fallback인
`index.html`을 받습니다:

```
OTS parsing error: invalid sfntVersion: 1008821359     ← 0x3C21444F, 즉 "<!DO"
Error: Soundfont is not a valid Soundfont2 file
```

그리고 아무것도 렌더되지 않습니다. **dev 서버를 재시작하면 멀쩡해집니다**(이제 파일이 부팅
시점에 이미 디스크에 있으니까). 그래서 증상이 간헐적으로 보이고 디버깅이 짜증납니다.

해결: 복사를 `scripts/alphatabAssets.ts`로 옮기고 **`vite.config.ts` 최상단에서 동기로**
호출합니다. config 평가는 서버 부팅보다 먼저라서 레이스가 원천적으로 사라집니다.
플러그인의 자체 복사는 `assetOutputDir: false`로 껐습니다(워커/워클릿 배선 때문에 플러그인
자체는 계속 씁니다).

`npm run test:cold`이 이 시나리오를 그대로 재현합니다 — public 에셋을 지우고, 새 dev 서버를
띄우고, 실제 브라우저로 열어서 `/font/Bravura.woff2`가 `wOF2` 매직으로 시작하는지,
`/soundfont/sonivox.sf3`가 `RIFF`로 시작하는지까지 봅니다. `MODE=preview`로 하면 빌드
경로도 같이 검증합니다.

교훈: warm 트리에서만 검증하면 콜드스타트 버그는 100% 놓칩니다.

## 함정 둘 — alphaTab은 CSS를 배포하지 않는다

재생 커서(`enableCursor`, `enableAnimatedBeatCursor`)를 켜도 아무 선이 안 보이는 이유:
alphaTab은 `.at-cursor-bar` / `.at-cursor-beat` 요소를 만들고 **위치와 크기는 인라인
transform으로 정확히 잡아주지만 색은 전혀 주지 않습니다.** CSS 파일 자체를 배포하지
않으니, 스타일을 직접 안 쓰면 선이 DOM에 있고 제대로 움직이는데도 완전히 투명합니다.

그래서 "커서 요소가 존재하고 transform이 맞다"는 검증으로는 아무것도 증명이 안 됩니다.
`npm run test:cursor`는 **computed background가 투명하지 않은지**와 재생 중 transform이
실제로 변하는지를 봅니다. 스타일은 `src/styles.css`의 "alphaTab 재생 커서" 절에 있고,
beat 커서 폭 3px과 centerAtPosition은 alphaTab이 정하므로 건드리지 않습니다.

## 함정 셋 — 선택적 의존성이 앱 전체를 죽인다

스템 분리를 붙이면서 `onnxruntime-web`과 `demucs-web`이 의존성으로 들어왔습니다.
`npm install`을 다시 안 돌린 상태로 실행하면 이런 게 뜹니다:

```
[plugin:vite:import-analysis] Failed to resolve import "onnxruntime-web"
```

그리고 **페이지가 완전히 백지가 됩니다.** 분리 기능만 안 되는 게 아니라 악보도 안 뜹니다.

이유: Vite는 동적 `import()`의 specifier도 **그 파일을 변환하는 시점에** 해석합니다.
그래서 `onnxruntime-web`을 언급하기만 해도 패키지가 없으면 모듈 변환이 실패하고,
`separator.ts`가 App의 정적 import 그래프에 얹혀 있었으니 앱 전체가 같이 죽었습니다.

**선택적 기능이 앱을 죽일 수 있으면 안 됩니다.** 그래서 ONNX를 언급하는 코드를
`demucsBackend.ts`로 격리하고, `separator.ts`의 `loadDemucsSeparator()`를 통해서만
닿게 했습니다. 이제 의존성이 빠져도 잃는 건 분리 버튼 하나고, 로컬 스템 가져오기 경로는
ONNX를 전혀 안 쓰므로 그대로 동작합니다.

`npm run test:degrade`가 두 패키지를 node_modules에서 빼내고 새 dev 서버를 띄워
앱이 여전히 렌더되는지 확인한 뒤 되돌려놓습니다.

## YouTube 링크 → 탭

### 준비 (한 번만)

```
py -m pip install -U "yt-dlp[default]"        REM Windows
python3 -m pip install -U "yt-dlp[default]"   # macOS / Linux
```

사이드카를 쓰는 Python에 깔아야 합니다 — `npm run sidecar` 첫 줄에 고른 인터프리터가
나오고, yt-dlp가 없으면 그 인터프리터용 설치 명령을 그대로 찍어줍니다. 분리(demucs)와
AI 채보(basic-pitch)까지 사이드카에서 돌리려면 같은 Python에 `demucs basic-pitch`도.

그다음 `start.bat`(또는 `npm run dev` + `npm run sidecar`)로 띄우고, 패널에 `yt-dlp`
배지가 보이면 준비 끝입니다. 사이드카를 앱보다 늦게 띄웠다면 패널의 **다시 확인**을 누르세요.

### 쓰는 법

1. 사이드바 맨 위 **YouTube 링크로 시작**에 링크 붙여넣기 → **가져오기**
2. 세 단계가 차례로 돕니다: **음원 받기 → 베이스 분리 → 탭 생성**. 진행률은 단계별로 보입니다.
3. 끝나면 새 곡이 영상 제목으로 "내 곡"에 저장되고, 화면에는 자동 생성된 탭이 떠 있고,
   소스는 "베이스만"으로 바뀌어 있습니다.

"받은 뒤 … 자동으로"를 끄면 음원만 받고 멈춥니다. 분리와 채보는 아래 패널 버튼으로
직접 — 사이드카 설정(모델·shifts)이나 BPM을 먼저 정하고 싶을 때 씁니다.

결과는 각각 파일로 받을 수 있습니다:

| 무엇 | 어디서 | 파일 |
|---|---|---|
| 음원 | YouTube 패널 "파일로 저장" | `<제목>.m4a` |
| 베이스 | 스템 분리 패널 "베이스 WAV 저장" | `<제목>-bass.wav` |
| 탭 | 상단 "탭 저장 (.gp)" | `<제목>.gp` (Guitar Pro 7 — Guitar Pro · TuxGuitar · MuseScore) |

### 왜 사이드카인가

브라우저는 YouTube 음원을 직접 읽을 수 없습니다. CORS가 막는 것도 있지만, 진짜 스트림
주소는 YouTube 자체 플레이어 JavaScript를 돌려야 풀리는 형태로 내려옵니다 — 그걸 푸는
게 정확히 yt-dlp의 일입니다. 그래서 다운로드만 로컬 사이드카가 하고, 받은 파일은 지금까지
"원본 음원"으로 넣던 파일과 똑같이 취급됩니다. 그 뒤 단계는 기존 코드 그대로입니다.

### 알아둘 것

- **YouTube 주소 해독에는 JavaScript 런타임이 필요합니다.** yt-dlp 기본값은 deno뿐인데,
  사이드카는 **지금 앱을 띄운 그 Node**를 yt-dlp에 같이 넘깁니다(`npm run sidecar`가
  경로를 전달). yt-dlp가 Node **22 이상**을 요구하니, 그보다 낮으면 Node를 올리거나
  [deno](https://deno.land)를 설치하세요.
- `pip install yt-dlp`만 하면 해독기(`yt-dlp-ejs`)가 빠져서 대부분의 영상이 서명 오류로
  실패합니다. 꼭 `"yt-dlp[default]"`로 까세요. 빠져 있으면 패널이 미리 알려줍니다.
- YouTube는 수시로 바뀌고 yt-dlp는 그걸 따라 자주 업데이트됩니다. 잘 되던 게 갑자기
  실패하면 먼저 `pip install -U "yt-dlp[default]"`.
- 받는 건 **영상 하나**입니다. 재생목록 링크(`list=`)나 시작 시각(`t=`)이 붙어 있어도
  영상 id만 남기고 버립니다. 30분 넘는 영상과 라이브 방송은 거절합니다.
- 음원은 m4a(AAC)를 우선으로 받습니다. 모든 브라우저가 재생·디코딩하고, 같은 곡 WAV의
  1/10 크기라 IndexedDB에 부담이 없습니다. 사이드카에 ffmpeg가 없으면 demucs가 m4a를 못
  읽으므로, 그때는 브라우저가 WAV로 바꿔서 보냅니다(자동).
- 본인이 연습용으로 쓸 권리가 있는 영상에만 쓰세요. 받은 파일은 이 컴퓨터 밖으로 나가지
  않습니다.

### 보안: 다른 사이트가 사이드카를 부릴 수 없게

사이드카는 `127.0.0.1`에만 열려 있어서 네트워크에서는 닿지 않지만, **브라우저에 열려 있는
아무 사이트나** localhost로 요청을 보낼 수는 있습니다. 그래서 두 겹으로 막습니다:

- **작업을 시작하는 요청(POST/DELETE)은 localhost 출처만 받습니다.** 브라우저는 교차 출처
  요청에 항상 `Origin`을 붙이니, 다른 사이트에서 온 건 403으로 끝납니다.
- **`/youtube`는 YouTube 호스트만 받습니다.** yt-dlp는 거의 아무 URL이나 받아오는 범용
  추출기를 갖고 있어서, 이게 없으면 사이드카가 "뭐든 대신 받아주는 로컬 프록시"가 됩니다.

`npm run test:youtube`가 둘 다 확인합니다.

## 스템 분리

원본에서 베이스를 뽑아내 소스를 넷으로 만듭니다.

| 소스 | 어디서 | 쓸모 |
|---|---|---|
| 신디 | 악보에서 생성 | 음/리듬 정확도 확인 |
| 원본 | 넣은 파일 | 밴드랑 맞춰 치기 |
| 베이스만 | 분리 결과 | 실제 연주자가 뭘 쳤는지 |
| 반주만 | 분리 결과 | 마이너스원 |

`S`로 원본↔신디, `B`로 베이스만↔반주만 토글됩니다.

### 왜 크로스페이드가 아니라 "하나만 선택"인가

스템을 동시에 울려 섞으려면 둘 사이 정렬이 ms 단위로 맞아야 합니다. `<audio>` 두 개는
서로 수십 ms씩 드리프트하고, 드럼 트랜지언트에서 그건 플램으로 들립니다. Web Audio
버퍼 소스로 가면 정렬은 구조적으로 완벽하지만 `AudioBufferSourceNode.playbackRate`에는
피치 보존이 없어서, 느리게 하면 음이 내려가고 속도 조절 기능과 정면으로 충돌합니다.

그래서 `AudioDeck`은 **전부 재생하되 하나만 들리게** 합니다. 스템 간 드리프트는 두 개를
동시에 들을 일이 없으니 관측 자체가 불가능해지고, 전환은 게인 변경뿐이라 재탐색도
디코딩 공백도 없습니다. 원래 고르셨던 Songsterr식 토글과도 맞습니다.

포기한 건 스템 간 연속 블렌드 하나입니다. 그건 버퍼 소스 + 스템마다 타임스트레치
워클릿이 필요하고, 별도 작업입니다.

### 로컬 사이드카 (권장)

브라우저 분리는 **고정된 양자화 모델 하나**만 돌립니다. 모델 선택도, shifts도, overlap도,
GPU도 없습니다. 그런데 스템이 깨끗하냐 끊기냐를 가르는 게 정확히 그 설정들입니다.

앱을 데스크톱 프로그램으로 갈아엎는 대신, 무거운 작업만 옆에서 도는 작은 로컬 프로세스에
맡깁니다. 웹앱은 그대로 두고요.

```
py -m pip install demucs        REM Windows
python3 -m pip install demucs   # macOS / Linux

npm run sidecar                 # 별도 터미널에서
```

> Windows에는 `python3` 명령이 없습니다 — Microsoft Store 스텁이 걸려서
> `WindowsApps\python3.exe을(를) 찾을 수 없습니다`라는 엉뚱한 에러를 냅니다.
> `npm run sidecar`는 `py -3` → `python` 순으로 알아서 찾으니 그대로 쓰시면 됩니다.

띄워두고 새로고침하면 스템 패널에 설정 상자가 나타납니다 — 모델, shifts, overlap을 직접
조절할 수 있고, GPU가 있으면 자동으로 씁니다. 안 띄워도 앱은 그대로 동작하며 브라우저
분리로 돌아갑니다.

자세한 건 [`sidecar/README.md`](sidecar/README.md).

**cross-origin 주의:** 앱 페이지는 SharedArrayBuffer 때문에 일부러 isolated 상태라,
사이드카 응답에는 CORS뿐 아니라 **CORP까지** 필요합니다. 둘 중 하나만 빠져도 fetch가
아무 설명 없는 네트워크 에러로 죽습니다. `npm run test:sidecar`가 실제 isolated 페이지에서
교차 출처 호출이 되는지 확인합니다 — curl로는 증명이 안 되는 부분입니다.

### 세 가지 분리 경로

**브라우저 분리** — 설치 없이 버튼 하나. 대신 첫 실행에 **약 200MB**를 받습니다
(ORT wasm 27MB + HTDemucs ONNX 172MB). 곡당 몇 분 걸립니다.

**로컬 Demucs 결과 가져오기** — 훨씬 빠르고 결과도 낫습니다. `bass.wav` **하나만**
주시면 됩니다. 반주는 `원본 - 베이스`로 계산하니 나머지 스템 파일은 필요 없습니다
(Demucs 스템은 가산적이라 이 뺄셈이 근사가 아니라 정확합니다).

### COOP/COEP — 필수가 아니라 속도 문제

**처음엔 이걸 필수 조건으로 잘못 걸었습니다.** isolation이 없으면 분리를 아예 거부했는데,
onnxruntime-web 번들을 뜯어보니 자체적으로 이렇게 처리하고 있었습니다:

```
numThreads > 1 && !multiThreadSupported  →  numThreads = 1
```

단일 스레드 세션은 SharedArrayBuffer가 필요 없습니다. 게다가 demucs-web이 첫 번째로
요청하는 **WebGPU 실행 경로는 SAB를 아예 안 씁니다.** 즉 WebGPU가 되는 브라우저에서는
isolation이 속도와도 무관합니다.

그래서 isolation이 실제로 정하는 건 **CPU 폴백이 멀티스레드를 쓸 수 있는지**뿐입니다.
세 가지 모드로 정리했고, 어느 경우든 분리는 실행됩니다:

| 모드 | 조건 | 속도 |
|---|---|---|
| WebGPU | WebGPU 사용 가능 | 가장 빠름, isolation 무관 |
| CPU 멀티스레드 | isolation 켜짐 | 중간 |
| CPU 단일 스레드 | isolation 꺼짐 | 느림 (결과는 동일) |

헤더는 `vite.config.ts`가 답니다. COEP는 `require-corp`가 아니라 **`credentialless`**인데,
require-corp는 CORP 헤더 없는 크로스오리진 리소스를 전부 거부해서 Hugging Face에서 모델
받는 걸 막아버리기 때문입니다. 모델을 `public/models/`에 두면 이 문제 자체가 없어집니다.

### 확장 프로그램이 isolation을 깬다

헤더가 정상적으로 도착하는데도 `crossOriginIsolated`가 false인 경우가 있습니다. 크롬
확장 프로그램이 페이지에 리소스를 주입하면 isolation이 깨집니다. 시크릿 창에서 되면
확장 프로그램이 범인입니다.

**단, 시크릿 창을 상시로 쓰면 안 됩니다** — 창을 닫을 때 IndexedDB가 지워져서 저장한
곡·앵커·스템이 전부 날아갑니다. 확장 없는 별도 크롬 프로필을 만드는 쪽이 맞습니다.
(그냥 느린 모드로 두셔도 결과는 같습니다.)

**isolation이 꺼져 있으면 스템 패널이 스스로 진단합니다.** 설정 파일을 믿지 않고 응답
헤더를 네트워크에서 다시 읽어서, 실제로 뭐가 도착했는지 표로 보여주고 원인을 한 줄로
짚습니다. 가장 흔한 원인이 **설정 파일이 바뀌기 전에 떠 있던 dev 서버**인데, 그 경우
설정은 완벽해 보이는데 응답에는 헤더가 없어서 원격으로는 진단이 거의 불가능합니다.

진단이 짚는 것들:

- 헤더가 아예 안 옴 → dev 서버 재시작
- 보안 컨텍스트 아님 → LAN IP 대신 localhost로 접속
- Safari + credentialless → require-corp로 변경
- 헤더는 왔는데 isolation 안 켜짐 → 확장 프로그램 의심, 시크릿 창

`npm run test:diag`가 헤더를 넣은 서버와 뺀 서버 양쪽에 앱을 붙여서, 진단이 두 경우 모두
진실을 말하는지 확인합니다. 틀린 원인을 짚는 진단은 없느니만 못하니까요.

### 검증 안 된 부분 (솔직히)

유닛 테스트가 증명하는 건 스템 수학과 WAV 코덱입니다 — 믹스다운, 뺄셈, 16비트 왕복,
클리핑 시 wrap 대신 clamp. 브라우저 테스트가 증명하는 건 전제조건과 UI 상태입니다.

**실제 분리 품질은 검증하지 못했습니다.** GPU와 200MB 다운로드가 필요한데 개발 환경에
둘 다 없습니다. 진짜 곡으로 직접 돌려보셔야 합니다.

## 자동 채보 — 귀는 둘, 손은 하나

### Songsterr가 실제로 하는 방식

탭이 정확한 이유는 알고리즘이 좋아서가 아닙니다. **사람이 Guitar Pro 파일로 찍고, 탭
에디터에서 고친 것**을 쌓아둔 겁니다. 거기에 별도로 **AI Transcribe**를 붙여서 오디오에서
*초안*을 만들어주고, 그 초안을 사람이 다듬습니다.

즉 "AI가 뽑은 걸 그대로 쓴다"가 아니라 **AI 초안 → 사람 수정 → 저장**이 구조입니다.
우리 쪽 정확도가 계속 아쉬웠던 진짜 이유가 여기 있습니다. 초안을 완성본으로 취급하고
있었으니까요.

그래서 구조를 같은 모양으로 바꿨습니다.

### 두 엔진, 하나의 필기 파이프라인

```
              ┌─ YIN (브라우저 내장, 설치 0)  ─┐
베이스 스템 ──┤                                ├─→ notesToAutoTab() ─→ alphaTex ─→ 악보
              └─ basic-pitch (사이드카, AI)  ─┘
```

| | YIN | basic-pitch |
|---|---|---|
| 어디서 | 브라우저 | 사이드카(Python) |
| 방식 | 자기상관 (신호처리) | 학습된 온셋+피치 신경망 (Spotify, Apache-2.0) |
| 설치 | 없음 | `pip install basic-pitch` |
| 강점 | 즉시, 오프라인 | 온셋이 훨씬 정확, 반복음 구분 |
| 약점 | 어택/반복음에 약함 | 설치 필요, 조금 느림 |

**중요한 건 오른쪽 절반이 완전히 공유된다는 점입니다.** 그리드 피팅, 양자화, 지판 배치,
alphaTex 작성 — 전부 `notesToAutoTab()` 하나를 지납니다. 귀만 바뀌고 필기는 안 바뀝니다.
그래서 아래쪽에서 정확도 문제를 잡으면 두 엔진 모두 같이 좋아집니다.

사이드카에 basic-pitch가 깔려 있으면 앱이 알아서 그쪽을 씁니다. 없으면 조용히 YIN으로
돌아갑니다. 어느 쪽이 썼는지는 결과 줄에 표시됩니다.

### 반복음을 붙이면 안 되는 이유 (실제로 밟았던 함정)

YIN 경로에는 `mergeNearbyNotes()`가 있습니다. 레벨 게이트가 한 음 한가운데를 잠깐 끊어
먹었을 때 다시 이어붙이는 용도입니다.

그걸 basic-pitch에도 똑같이 적용했더니 **같은 음 반복이 전부 하나의 긴 음으로 뭉쳤습니다.**
근음을 8분음표로 계속 퉁기는 건 베이스에서 가장 흔한 패턴인데 그게 통째로 날아간 겁니다.

basic-pitch는 온셋을 *명시적으로* 검출합니다. 짧은 공백 뒤의 같은 음은 게이트 사고가 아니라
진짜 다시 친 음입니다. 그래서 병합은 YIN 전용으로 못박았고, `npm run test:sidecar`가
스텁이 낸 A1 4개가 4개로 남는지 매번 확인합니다.

### 템포는 추측이 아니라 탐색으로 찾는다

첫 버전은 **onset 간격의 중앙값**으로 BPM을 잡았습니다. 그럴듯해 보였고 완전히 틀렸습니다.
중앙값은 음악적인 값이 아닙니다 — 8분음표와 4분음표가 섞인 라인에서는 둘 사이 어딘가에
떨어지고, 그건 어느 쪽도 아닙니다.

실제 곡(552음표)에서 이렇게 나왔습니다:

| | 격자 오차 | 격자 강도 |
|---|---|---|
| 중앙값 방식 → 112.4 BPM | ±33.2ms | 0.02 (= 무작위) |
| 전역 탐색 → **146.0 BPM** | **±11.5ms** | **0.77** |

지금 방식은 60–200 BPM을 전부 훑으면서, 각 후보 격자에 **모든 온셋을 한꺼번에** 대봅니다.
온셋을 격자 안 위상의 단위벡터로 바꿔 더하면, 격자에 맞는 것들은 같은 방향을 가리켜 쌓이고
흩어진 것들은 상쇄됩니다. atan2 한 번이 최적 위상이라 후보마다 위상 탐색을 따로 할 필요도
없습니다.

**격자 강도**가 이 작업의 핵심 산출물입니다. BPM은 뭘 넣어도 항상 숫자 하나가 나오지만,
강도는 그게 *찾아낸* 값인지 그냥 *뱉은* 값인지를 말해줍니다. 0.35 미만이면 리듬을 믿지
말라고 화면에 띄웁니다.

> 만드는 도중에 배운 것: 후보를 많이 훑으면 **아무 온셋에나 맞는 격자가 하나쯤 나옵니다.**
> 무작위 10개가 0.75를 받았습니다. 그래서 강도는 "후보 N개 중 최고가 무작위 데이터에서 받을
> 점수"를 빼고 보고합니다. 그 바닥값은 음표 수의 제곱근에 반비례해서 떨어집니다.

### 격자를 찾는 것과 템포를 아는 것은 다른 질문이다

**이걸 하나로 취급한 게 두 번째 버그였습니다.** 탐색기가 "16분음표 = 박÷4"를 전제로 깔고
있었거든요.

Green Day의 Holiday로 확인했습니다. 베이스가 전부 8분음표라 녹음에 존재하는 가장 작은
격자는 **205ms**입니다. 그런데 205ms를 60~200 BPM 사이 어떤 곡의 16분음표로도 부를 수
없습니다 — 유일한 방법이 109.8 BPM의 *3연음*으로 부르는 거죠. 그래서 옛 코드는 정확히
그렇게 했습니다. Songsterr가 146이라고 적어둔 곡에 **109.77**을 붙이고, 모든 마디선을
있어야 할 자리의 4분의 3 지점에 그었습니다.

| | 실측 |
|---|---|
| 우리 BPM | 109.77 |
| 146 × ¾ | 109.5 |
| 리프 반복 주기 | 6.56초 = **146에서 정확히 4마디**, 109.77에서는 2.98마디 |
| 그 절반 | 3.28초 = **146에서 2마디**, 109.77에서는 1.49마디 |

**1.49마디짜리 프레이즈는 존재하지 않습니다.** 여기서 판정이 끝납니다.

지금은 **박이 아니라 격자 간격 자체를 탐색**하고, 그 간격이 한 박에 몇 개 들어가는지를
따로 정합니다(2·3·4·6). 온셋만으로는 이걸 정할 수 없으니 — 같은 자리에 같은 음을 놓는
설명이 여러 개라서 — **편곡에 물어봅니다.** 베이스 라인은 반복되고, 반복은 정수 마디로
떨어지며, 거의 항상 2·4·8마디입니다. 리프 반복 주기를 재서 그게 온전한 마디 수로 나오는
쪽을 고릅니다.

> 여기서도 하나 배웠습니다. 자기상관은 **진짜 주기의 배수도 똑같이 잘 맞습니다.** 2마디
> 리프가 6마디로 돌아왔고, 6은 프레이즈 길이가 아니라서 탐색기가 그걸 4마디로 만들어주는
> 엉뚱한 템포를 선호했습니다. 이제 같은 점수를 내는 가장 짧은 주기로 내려갑니다.

그리고 셔플에는 3분할 격자가 필요합니다. 다만 **3연음 괄호로 적지는 않습니다** — Songsterr도,
세상의 모든 페이크북도 직선 8분음표로 적고 맨 위에 셔플 표시만 붙입니다. 매 박마다 3연음
괄호가 있는 악보는 읽을 수가 없거든요. 대신 직선 쪽으로 기본값을 두었습니다. 어떤 직선
격자든 "세 배 느린 박을 3등분한 것"으로 설명할 수 있어서, 증거 없이는 셔플로 읽지 않습니다.

### 쉼표 도배를 없앤다

검출된 길이는 그 음이 **들린** 시간입니다. 베이스는 뜯으면 감쇠하니 연주자가 손을 떼기
훨씬 전에 잘리고, 남은 자리가 전부 쉼표가 됩니다. 음표마다 쉼표가 하나씩 붙은 악보가
나오는 이유죠. 사람은 다음 음이 올 때까지 이어서 적습니다. 한 박을 넘는 공백만 진짜
쉼표로 남깁니다 — 연주자가 쉰 마디는 쉼표로 남아야 하니까요.

### 반 박자 / 두 배 박자는 사람이 정한다

146 BPM의 8분음표와 73 BPM의 16분음표는 **같은 격자**입니다. 온셋만 봐서는 구분할 방법이
원리적으로 없습니다 — 둘 다 맞으니까요. 자동으로는 사람이 더 흔히 쓰는 쪽(비트 주기가
500ms 근처)을 고르고, 화면에 **템포 ÷2 / ×2** 버튼을 둡니다. 이미 검출한 음표를 다시 쓰기
때문에 즉시 끝납니다.

### 옥타브 오검출은 되돌린다

자기상관은 기음이 약하면 2배음으로 미끄러집니다. 분리된 스템은 저역이 깎여 있어서 자주
그렇습니다. 프레임 단위 스무딩으로는 안 잡힙니다 — 한두 프레임이 아니라 **음표 하나 전체가**
통째로 올라가서, 깔끔하고 확신에 찬 틀린 음으로 도착하거든요. 실제 곡에서 552개 중 28개(5%)가
앞뒤 음보다 정확히 한 옥타브 위에 앉아 있었습니다.

되돌리되, **진짜 옥타브 주법은 건드리면 안 됩니다.** 디스코 옥타브나 펑크 팝은 베이스의
기본기니까요. 네 조건이 동시에 맞을 때만 내립니다: 앞뒤 *양쪽* 보다 한 옥타브 위 · 내리면
이웃 음의 온음 안에 들어옴 · 앞뒤와 시간상 붙어 있음 · **앞뒤보다 짧음**. 진짜 옥타브
주법은 마지막 조건에서 걸러집니다. `E1 E2 E1`은 셋 다 길이가 비슷하지만, 배음 미끄러짐은
긴 음 안에서 잠깐 튀는 거라 짧습니다.

### 못 잡은 구간을 쉼표로 위장하지 않는다

검출기가 놓친 구간은 악보에서 **연주자가 쉰 마디와 똑같이 생겼습니다.** 그래서 음이 잡힌
구간의 비율과 가장 긴 공백을 같이 재서, 13초짜리 구멍이 있으면 그렇다고 말합니다. 인트로와
아웃트로는 빼고 셉니다 — 모든 곡에서 울리는 경보는 무시하게 되니까요.

### 정확도가 아쉬울 때 순서대로

1. **스템부터** — 채보는 스템보다 좋아질 수 없습니다. `htdemucs_ft` + shifts 2 + overlap 0.5.
2. **basic-pitch 설치** — 온셋 정확도 차이가 가장 큽니다.
3. **격자 강도부터 보기** — 낮으면 BPM을 직접 넣으세요. 폭이 고정되면 위상만 맞추면 됩니다.
4. **마디가 두 배로 느껴지면** 템포 ÷2 / ×2.
5. **진단 JSON 내보내기** — 들린 음 전부가 시각·확신도와 함께 나옵니다.

### 진단 JSON 다시 돌려보기

```
npm run replay -- 채보진단.json
npm run replay -- 채보진단.json --bpm 146
```

진단 파일에는 검출기가 들은 음이 전부 들어있고, 그게 곧 그 아래 단계 전부의 입력입니다.
그래서 오디오도 스템도 없이 **필기 파이프라인만 밀리초 단위로 다시 돌릴 수 있습니다.**
합성 테스트가 아니라 진짜 곡에 대고요. 위 표의 숫자가 전부 여기서 나왔습니다.

중요한 건 이 도구가 `notesToAutoTab`을 **그대로 호출한다**는 점입니다. 재현 도구가 측정
대상을 다시 구현하면, 고쳐지지도 않은 버그를 고쳐졌다고 신나게 보고합니다.

## 왜 이렇게 짰는지 (나중의 나를 위한 메모)

### 1. alphaTab은 항상 `PlayerMode.EnabledSynthesizer`. 절대 안 바꾼다.

alphaTab 1.6+에는 백킹 트랙 모드(`EnabledBackingTrack`, `EnabledExternalMedia`)가 있고
겉보기엔 그게 정답 같습니다. 그런데 소스 코드를 보면 `playerMode`가 바뀔 때
`_setupOrDestroyPlayer()`가 플레이어를 **통째로 부수고 다시 만듭니다.** 그러면 MIDI를 다시 굽고
사운드폰트도 다시 올려야 합니다. Songsterr의 소스 전환은 즉시인데, 여기에 1~2초 리빌드가
끼면 연습 도구로 못 씁니다.

그래서 alphaTab은 **트랜스포트 마스터**로 고정해두고 (재생/정지, 커서, 루프, 속도, 메트로놈,
카운트인 전부 alphaTab 것), 원본 음원은 별도 `<audio>`로 **따라오게** 했습니다.
전환은 게인 두 개 조절이 전부라 즉각적이고 끊기지 않습니다.

덤: 크로스페이드가 공짜로 딸려옵니다. 같은 게인 두 개를 슬라이더로 노출한 게 "믹스" 버튼입니다.

대가는 **드리프트**입니다. 시계가 둘이니 벌어집니다. `src/lib/originalTrack.ts`의 `syncTo()`가
처리합니다 — 오차 120ms 넘으면 그냥 점프, 12~120ms면 재생속도를 최대 0.5%만 흔들어서
슬금슬금 당깁니다(0.5%면 피치 변화가 안 들립니다), 12ms 안쪽이면 건드리지 않습니다.
사이드바의 "실시간 오차"가 이 동작을 그대로 보여주니 값이 마음에 안 들면 상수만 바꾸세요.

### 2. 싱크는 tick ↔ audio ms 구간별 선형 보간 하나뿐

`src/lib/syncmap.ts`. 앵커 2개면 "시작점 + 고정 템포"고, 앵커를 늘리면 그대로 비트맵이 됩니다.
**둘 사이에 코드 차이가 없습니다.** 라이브 녹음이라 뒤로 갈수록 밀리면 밀리는 지점에
앵커 하나 더 찍으면 끝입니다.

시간이 아니라 tick 공간에서 매핑하는 이유: 속도를 0.7배로 낮추면 신디의 tick 진행과
오디오의 미디어 시간이 **같은 비율로** 느려지므로 tick → ms 맵은 속도와 무관합니다.
시간 → 시간 맵이었으면 속도 바꿀 때마다 다시 계산해야 합니다.

"앵커 2개만 썼다면 ±N ms 어긋남" 계기판(`driftIfLinear`)이 앵커를 더 찍어야 하는지
알려줍니다. 곡 내내 30ms 안쪽이면 2개로 충분합니다.

### 3. 앵커는 bar가 아니라 synth tick으로 저장

alphaTab의 공식 저장 포맷은 `FlatSyncPoint = { barIndex, barPosition, barOccurence,
millisecondOffset }`로 마디 상대 좌표입니다. 호환에는 좋은데 **찍을 때가 곤란합니다** —
도돌이표가 있으면 같은 마디가 여러 번 지나가서 방금 들은 게 몇 회차인지 풀어야 합니다.

그래서 실제로 측정한 값인 raw synth tick(alphaTab MIDI 생성기가 도돌이를 이미 펼쳐놓은
좌표)을 저장하고, 마디 정보는 표시용으로만 같이 답니다. `SyncAnchor`가 `FlatSyncPoint`의
상위집합이라 나중에 `score.applyFlatSyncPoints()`로 내보내는 변환만 붙이면 됩니다.

### 4. 타임스트레치는 지금 브라우저가 공짜로 해준다

alphaTab 문서에 "오디오 자체는 변형하지 않는다"고 되어 있어서 느리게 하면 피치가 내려갈 것
같지만, `<audio>`의 `preservesPitch`가 최신 브라우저 기본값 true라 브라우저가 알아서
타임스트레치합니다. 0.7배까지는 쓸 만하고 0.5배 밑에서 뭉개집니다.

더 필요해지면 **`src/lib/originalTrack.ts` 안쪽만** 갈아끼우면 됩니다 —
[signalsmith-stretch](https://signalsmith-audio.co.uk/code/stretch/) (MIT, WASM AudioWorklet,
실시간용으로 0.75~1.5배 최적화)를 AudioWorklet으로 물리고 나머지는 그대로 두면 됩니다.
바깥 코드는 이 클래스의 인터페이스만 알고 있습니다.
